## Overview

The Sale Dispatches module handles physical delivery of goods from warehouse sites to customers after a sale is created. Each dispatch corresponds to a **single site** — if a sale's reserved stock spans multiple sites, one dispatch is created per site automatically.

| Sub-module | Base Path | Description |
|---|---|---|
| Sale Dispatches | `/sale-dispatches` | Generate, list, view, and update dispatches |

### Relationship to Sales

A `SaleDispatch` is always linked to a `Sale`. The typical workflow:

1. Create a `Sale` (stock is FIFO-reserved at product level).
2. Call **Generate Dispatches** (`POST /sale-dispatches/generate/:saleId`) — the system allocates the reserved stock to specific batches per site and creates one dispatch per site.
3. Approve each dispatch (`PATCH` with `status: "APPROVED"`).
4. Mark as delivered (`PATCH` with `status: "DELIVERED"`) — stock is physically deducted at this point.

### Dispatch Number Format

Auto-generated by the backend: `SD-YYYYMMDD-XXXX` (daily-sequential, zero-padded to 4).

Examples: `SD-20260618-0001`, `SD-20260618-0002`

## Enums & Constants

### `SaleDispatchStatus`

```
DRAFT      — Dispatch created; batch reservations held; editable
APPROVED   — Dispatch approved for delivery; can be rejected back to DRAFT
DELIVERED  — Dispatch physically delivered; stock deducted; terminal
```

### Status Transition Rules

| From | To | Notes |
|---|---|---|
| `DRAFT` | `APPROVED` | Standard approval |
| `APPROVED` | `DRAFT` | Reject / send back for correction |
| `APPROVED` | `DELIVERED` | Mark as delivered — triggers stock deduction |
| `DELIVERED` | *(any)* | **Blocked** — delivered dispatches cannot be modified |

```
                    │  POST /sale-dispatches/generate/:saleId       │

                     /         \
         PATCH status=DRAFT    PATCH status=DELIVERED
         (reject back)              │
                                [DELIVERED]  ← terminal; stock deducted
```

## 1. Generate Dispatches

```
POST /sale-dispatches/generate/:saleId
Permission: sale-dispatches.create
```

Auto-generates one `SaleDispatch` per site from the FIFO batch reservations already held by the sale. Each dispatch contains batch-level line items showing exactly which batch contributes how many units.

**Pre-conditions:**
- The sale must exist.
- No `DRAFT` or `APPROVED` dispatches may already exist for this sale. Delete or cancel them before regenerating.
- Every PRODUCT item on the sale must have sufficient available batch stock (with a `siteId`) to cover the remaining un-dispatched quantity.

**What happens on generate:**
1. For each product item on the sale, the system finds all `ACTIVE` batches with `availableQuantity > 0` and a non-null `siteId`, ordered `createdAt ASC` (FIFO).
2. Batch allocations are grouped by `siteId`.
3. One `SaleDispatch` is created per site with `status: DRAFT`.
4. For each allocated batch: `availableQuantity` is decremented and `reservedQuantity` is incremented (batch-level reservation).
5. The creator is automatically set as the initial `dispatchOfficer`.

### Path Parameter

| Param | Type | Notes |
|---|---|---|
| `saleId` | `uuid` | ID of the `COMPLETED` or `DRAFT` sale to dispatch |

### Request Body

No body required.

### Response `201 Created`

Returns an **array** of all created dispatches (one per site), each in full detail shape.

## 4. Update Dispatch

```
PATCH /sale-dispatches/:saleDispatchId
Permission: sale-dispatches.update
```

Single endpoint that handles three types of operations depending on the `status` field and current dispatch state.

### Path Parameter

| Param | Type | Notes |
|---|---|---|
| `saleDispatchId` | `uuid` | Dispatch ID |

### Request Body

```json
{
  "status": "APPROVED",
  "dispatchOfficerId": "user-uuid",
  "notes": "Ready for pickup"
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `status` | `SaleDispatchStatus` | No | `APPROVED`, `DRAFT`, or `DELIVERED` — see transition rules below |
| `dispatchOfficerId` | `uuid` | No | User ID of the officer handling the dispatch. **DRAFT only.** |
| `notes` | `string` | No | Free-text notes. **DRAFT only.** |

### Operation A — Approve (`DRAFT → APPROVED`)

```json
{ "status": "APPROVED" }
```

Sets `approvedAt` to current timestamp.

**Response `200 OK`**: Full dispatch (same shape as [Get Single Dispatch](#3-get-single-dispatch) but raw repository shape, i.e. `items` are flat rows, user IDs are not resolved).

---

### Operation B — Reject / Send Back (`APPROVED → DRAFT`)

```json
{ "status": "DRAFT" }
```

Clears `approvedAt` back to `null`. Use this to send a dispatch back for correction.

**Response `200 OK`**: Full dispatch with `status: "DRAFT"` and `approvedAt: null`.

---

### Operation C — Mark Delivered (`APPROVED → DELIVERED`)

```json
{ "status": "DELIVERED" }
```

This is the **stock deduction step**. The following side effects happen atomically:

1. For each `SaleDispatchItem`:
   - `ProductBatch.reservedQuantity` decremented by item `quantity`.
   - `ProductBatch.consumedQuantity` incremented by item `quantity`.
2. For each affected product:
   - `Product.currentStock` decremented by total dispatched quantity.
   - `Product.reservedStock` decremented by total dispatched quantity.
   - A `StockTransaction` of type `SALE` is created (with `referenceNo = dispatchNumber`).
3. For each `SaleItem` touched by the dispatch:
   - `SaleItem.dispatchedQuantity` incremented by the dispatched quantity.
4. `SaleDispatch.status` → `DELIVERED`, `deliveredAt` → current timestamp.

**Response `200 OK`**: Full dispatch with `status: "DELIVERED"` and `deliveredAt` set.

---

### Operation D — Edit Officer / Notes (`DRAFT` only)

```json
{
  "dispatchOfficerId": "user-uuid-new-officer",
  "notes": "Updated handling instructions"
}
```

Can be sent without a `status` field, or combined with a `status` change. Only allowed when dispatch is `DRAFT`.

**Response `200 OK`**: Full updated dispatch.

### Response Shape (PATCH)

The PATCH endpoint returns the **raw repository detail shape** (not the grouped/enriched shape from GET single). Differences from `GET /sale-dispatches/:saleDispatchId`:

- User fields (`siteManagerId`, `dispatchOfficerId`, `createdById`) are returned as **IDs** (not resolved name objects).

## FIFO Batch Allocation & Stock Flow

### Phase 1 — Generate (Batch-Level Reserve)

Triggered by `POST /sale-dispatches/generate/:saleId`.

1. For each PRODUCT item on the sale, the system fetches all `ACTIVE` batches with `availableQuantity > 0` and a `siteId`, ordered by `createdAt ASC` (oldest first — FIFO).
2. Batches are allocated greedily until the item's remaining un-dispatched quantity is filled.
3. Allocations are grouped by `siteId` → one `SaleDispatch` per site.
4. For each allocated batch: `availableQuantity ↓`, `reservedQuantity ↑`.
5. Product-level stock (`currentStock`, `reservedStock`) is **not changed** here — that already happened at sale creation.

### Phase 2 — Approve (No Stock Change)

Triggered by `PATCH` with `status: "APPROVED"`.

No stock is moved. `approvedAt` is stamped. This is purely an authorization checkpoint.

### Phase 3 — Deliver (Reserve → Consume)

Triggered by `PATCH` with `status: "DELIVERED"`.

For each allocated batch:
- `reservedQuantity ↓`, `consumedQuantity ↑`

For each product:
- `currentStock ↓`, `reservedStock ↓`
- A `StockTransaction` (type `SALE`) is created referencing the dispatch number.

For each sale item:
- `dispatchedQuantity ↑` by the total quantity dispatched across all batches for that item.

### Phase 4 — Reject (APPROVED → DRAFT, No Stock Change)

Triggered by `PATCH` with `status: "DRAFT"` from `APPROVED`.

No stock movement. `approvedAt` is cleared.

> **Important**: There is currently no "cancel dispatch" endpoint. A `DRAFT` dispatch cannot be deleted from the frontend — contact the backend if you need to remove erroneously created dispatches.

## Frontend Implementation Notes

### Status Badge Colors (suggested)

| Status | Color |
|---|---|
| `DRAFT` | Gray |
| `APPROVED` | Blue/Teal |
| `DELIVERED` | Green |

### Two Distinct Response Shapes

The list endpoint, generate endpoint, and PATCH endpoint all return **different item shapes** compared to the single GET:

| Endpoint | `items` shape | Users resolved? |
|---|---|---|
| `GET /sale-dispatches` | No items (list view) | No |
| `POST /sale-dispatches/generate/:saleId` | Flat `SaleDispatchItem[]` | No |
| `PATCH /sale-dispatches/:saleDispatchId` | Flat `SaleDispatchItem[]` | No |
| `GET /sale-dispatches/:saleDispatchId` | Grouped `DispatchGroupedItem[]` | Yes |

**Recommendation**: After a generate or PATCH, always refetch via `GET /sale-dispatches/:saleDispatchId` to display the enriched detail view.

### Typical Screen Flows

**Dispatch List Screen**
- `GET /sale-dispatches` with `search`, `status`, `saleId`, `siteId`, pagination controls.
- Show `dispatchNumber`, `sale.saleNumber`, `site.name`, `status`, `createdAt`.
- Click a row → navigate to dispatch detail.

**Dispatch Detail Screen**
- `GET /sale-dispatches/:saleDispatchId`.
- Show sale info (`saleNumber`, `customer.name`), site info (`name`, `location`).
- Show `dispatchOfficer.name`, `siteManager.name`, `createdBy.name`.
- Items table: one row per `item` in `items[]` showing `itemName`, `sku`, `orderedQuantity`, `dispatchedQuantity`, and a nested batch breakdown.
- Status action buttons (see table below).

**Status Action Buttons**

| Current Status | Available Actions | PATCH body |
|---|---|---|
| `DRAFT` | Approve | `{ "status": "APPROVED" }` |
| `DRAFT` | Edit officer | `{ "dispatchOfficerId": "..." }` |
| `DRAFT` | Edit notes | `{ "notes": "..." }` |
| `APPROVED` | Reject (send back) | `{ "status": "DRAFT" }` |
| `APPROVED` | Mark Delivered | `{ "status": "DELIVERED" }` |
| `DELIVERED` | *(none — read only)* | — |

**Generate Dispatches Flow** (typically triggered from the Sale detail screen)

1. Show a "Generate Dispatches" button on the sale detail when no active dispatches exist.
2. `POST /sale-dispatches/generate/:saleId` — on success, navigate to the dispatches list filtered by `saleId`.
3. If the error is "Active dispatches already exist", show a message: *"Dispatches already exist for this sale. View them in the Dispatches tab."*

**Viewing Dispatches for a Sale**

Use `GET /sale-dispatches?saleId=<sale-uuid>` to show all dispatches linked to a specific sale (e.g., a "Dispatches" tab on the Sale detail screen).

### `dispatchedQuantity` vs `orderedQuantity`

On the dispatch detail, each item shows:
- `orderedQuantity` — the original quantity from the sale line item.
- `dispatchedQuantity` — how much has already been confirmed as **DELIVERED** across all dispatches.

If `dispatchedQuantity < orderedQuantity`, the item is partially dispatched (remaining units may be in another dispatch or awaiting dispatch).

### Batch Breakdown Display

Each `item.batches[]` entry tells the frontend which specific batch contributes what quantity. This is useful for:
- Warehouse staff to know which physical batch to pick from.
- Traceability / audit purposes.

Display as a sub-table or tooltip on the items table:

```
Cotton Shirt (10 units total from this dispatch)
  ├─ BTH-20260101-0001  →  6 units
  └─ BTH-20260201-0001  →  4 units
```
