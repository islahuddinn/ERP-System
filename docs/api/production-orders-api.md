## Overview

A **Production Order** turns raw materials into finished products following a **BOM (Bill of Materials)**. The
backend handles all costing and stock math automatically:

- On **create**, it calculates exactly how much of each raw material is needed (including wastage %), allocates
  stock from existing raw material batches using **FIFO** (oldest received / soonest-expiring batch first), and
  **soft-reserves** that stock.
- On **confirm**, the reserved stock is physically consumed (deducted from inventory).
- While **in progress**, additional costs (labour, overhead, utilities) and reused waste materials can be added
  at any time — totals recalculate automatically.
- On **complete**, the operator enters the actual quantity produced, and the backend computes the final
  **cost per unit**.
- **cancel** can roll back a DRAFT (release reservations) or an IN_PROGRESS order (reverse consumption,
  restoring stock) — no records are ever deleted.

The frontend does **not** do any cost or stock math — it only displays values returned by the API and submits
simple action calls (`confirm`, `complete`, `cancel`, `costs`, `wastes`).

## Enums & Constants

### `ProductionOrderStatus`

```
DRAFT       — Created, raw materials reserved but not yet consumed. Editable (siteId, notes).
IN_PROGRESS — Confirmed; raw materials physically consumed from stock. Costs/wastes can be added.
COMPLETED   — producedQuantity recorded, costPerUnit calculated. Costs/wastes can still be added (recalculates costPerUnit).
CANCELLED   — Terminal. Reservations released (if was DRAFT) or consumption reversed (if was IN_PROGRESS).
```

#### Allowed Transitions

```
DRAFT       --confirm-->   IN_PROGRESS
DRAFT       --cancel -->   CANCELLED   (releases reservations)
IN_PROGRESS --complete-->  COMPLETED
IN_PROGRESS --cancel -->   CANCELLED   (reverses consumption, restores stock)
COMPLETED   --cancel -->   ❌ not allowed
CANCELLED   -->            ❌ terminal, no further actions
```

### `ProductionCostType` (for "Add Cost Line")

```
LABOUR
OVERHEAD
UTILITY
OTHER
```

### Order Number Format

Auto-generated by the backend. Pattern: `PROD-XXXXXX` (zero-padded sequence)
Example: `PROD-000123`

## The Full Lifecycle (A to Z Worked Example)

This worked example mirrors exactly what the backend does — useful for building a "cost breakdown" UI that
makes sense to a non-technical user.

**Scenario**: produce 100 "Wooden Chairs". The active BOM for Wooden Chair has one item: "Wood Plank",
`quantityPerUnit = 2.2`, `wastagePercent = 5%`.

### Step 1 — `requiredQuantity` (computed at create)

```
requiredQuantity = plannedQuantity × quantityPerUnit × (1 + wastagePercent / 100)
                 = 100 × 2.2 × 1.05
                 = 231 pcs of Wood Plank
```

### Step 2 — FIFO batch allocation (computed at create)

Available "Wood Plank" batches, ordered by expiry date then received date (oldest/soonest-expiring first):

| Batch | Received | Available qty | Unit cost |
|---|---|---|---|
| B1 | 2026-05-01 | 150 pcs | $10 |
| B2 | 2026-05-15 | 100 pcs | $12 |

Allocating 231 pcs takes from B1 first, then B2:

| Batch | Allocated qty | Line cost |
|---|---|---|
| B1 | 150 pcs | 150 × $10 = $1,500 |
| B2 | 81 pcs | 81 × $12 = $972 |
| **Total** | **231 pcs** | **rawMaterialCost = $2,472** |

> If total available stock across all batches is **less than** 231 pcs, the entire create request fails with a
> `400 Bad Request` (shortfall reported) — **nothing is persisted**, no partial order is created.

### Step 3 — records created (status = `DRAFT`)

**ProductionOrder** (header):

| Field | Value |
|---|---|
| `orderNumber` | `PROD-000123` |
| `status` | `DRAFT` |
| `plannedQuantity` | 100 |
| `producedQuantity` | 0 |
| `rawMaterialCost` | 2472 |
| `additionalCost` | 0 |
| `wasteInputCost` | 0 |
| `totalCost` | 2472 (= rawMaterialCost + additionalCost + wasteInputCost) |
| `costPerUnit` | `null` |

**ProductionOrderMaterial** (one row per BOM item):

| rawMaterial | requiredQuantity | estimatedCost |
|---|---|---|
| Wood Plank | 231 | 2472 |

**ProductionOrderMaterialBatch** (one row per FIFO allocation; each batch's `reservedQuantity` is bumped — a
soft reservation, physical stock untouched until confirm):

| material | batch | allocatedQty | cost |
|---|---|---|---|
| Wood Plank | B1 | 150 | 1500 |
| Wood Plank | B2 | 81 | 972 |

### Step 4 — `confirm()`: DRAFT → IN_PROGRESS

For each `ProductionOrderMaterialBatch` row, the reservation becomes real consumption: batch stock is physically
deducted, `startedAt` is set. **Totals do not change** — they were locked in at create time.

### Step 5 — `addCost()`: record extra costs while IN_PROGRESS

Example: electricity cost of $200.

| Field | Before | After |
|---|---|---|
| `rawMaterialCost` | 2472 | 2472 |
| `additionalCost` | 0 | 200 |
| `wasteInputCost` | 0 | 0 |
| `totalCost` | 2472 | 2672 |

`additionalCost` = sum of **all** `ProductionOrderCost` rows for this order.

### Step 6 — `addWaste()`: reuse a pending waste record as production input

Example: 10 pcs of reclaimed Wood Plank @ $8/pc ($80 total) from a prior `PENDING` `WasteManagement` record is
consumed as input. That waste record is marked `REUSED`.

| Field | Before | After |
|---|---|---|
| `rawMaterialCost` | 2472 | 2472 |
| `additionalCost` | 200 | 200 |
| `wasteInputCost` | 0 | 80 |
| `totalCost` | 2672 | 2752 |

`wasteInputCost` = sum of **all** `ProductionOrderWaste` rows for this order.

> `addCost()` and `addWaste()` can be called **multiple times, in any order**, any number of times, as long as
> the order is not `CANCELLED` — including after `complete()`.

### Step 7 — `complete()`: IN_PROGRESS → COMPLETED

The operator records the actual output, e.g. `producedQuantity = 95` (some loss occurred).

```
costPerUnit = totalCost / producedQuantity
            = 2752 / 95
            = 28.97 (per chair)
```

| Field | Value |
|---|---|
| `producedQuantity` | 95 |
| `totalCost` | 2752 |
| `costPerUnit` | 28.97 |
| `status` | `COMPLETED` |
| `completedAt` | now() |

If `addCost()` / `addWaste()` are called **after** completion (e.g. a late invoice), `recalculateCosts()` runs
again and **also refreshes `costPerUnit`** using the already-recorded `producedQuantity`.

### Step 8 — `cancel()`: DRAFT or IN_PROGRESS → CANCELLED

- If the order was `DRAFT`: every reserved batch allocation is released back to available stock — nothing was
  physically consumed, so nothing to reverse.
- If the order was `IN_PROGRESS`: every consumed batch allocation is reversed, restoring physical stock.
- `COMPLETED` or already-`CANCELLED` orders **cannot** be cancelled (`400 Bad Request`).

## Production Orders API

### 1. Create Production Order

```
POST /production-orders
Permission: production-orders.create
```

Performs Steps 1–3 above: validates the BOM, calculates required quantities, allocates FIFO batches, and creates
the order in `DRAFT` status.

#### Request Body

```json
{
  "productId": "11111111-1111-1111-1111-111111111111",
  "bomId": "22222222-2222-2222-2222-222222222222",
  "siteId": "33333333-3333-3333-3333-333333333333",
  "plannedQuantity": 100,
  "notes": "Production run for June batch"
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `productId` | `uuid` | Yes | Finished product to produce |
| `bomId` | `uuid` | Yes | Must be an **ACTIVE** BOM belonging to `productId`. Pick this from the BOM dropdown for the selected product |
| `siteId` | `uuid` | No | Site where production happens / output is stored |
| `plannedQuantity` | `number` | Yes | Must be > 0. Quantity of finished product to produce |
| `notes` | `string` | No | Free text |

#### Response `201 Created`

Full production order object — see [Get Single Production Order](#3-get-single-production-order) for the
complete shape (includes `materials`, `costs`, `wastes`, `product`, `bom`, `site`).

#### Validation Errors `400 Bad Request`

```json
{ "message": "BOM has no items to produce from" }
{ "message": "Insufficient stock for raw material \"Wood Plank\": need 231, short by 81" }
```

```json
{
  "statusCode": 404,
  "message": "No active BOM found for this product",
  "error": "Not Found"
}
```

> If a `400`/`404` is returned, **no order was created** — nothing to clean up on the frontend.

### 5. Confirm Production Order

```
POST /production-orders/:productionOrderId/confirm
Permission: production-orders.update
```

Moves `DRAFT` → `IN_PROGRESS`. Converts all reserved batch allocations into actual stock consumption and sets
`startedAt`. No request body.

#### Path Parameter

| Param | Type | Notes |
|---|---|---|
| `productionOrderId` | `uuid` | Must currently be `DRAFT` |

#### Response `200 OK`

Full updated production order object — `status: "IN_PROGRESS"`, `startedAt` set, each `materials[].batchAllocations[].consumedAt` populated, `materials[].consumedQuantity` now equals `requiredQuantity`.

#### Validation Error `400 Bad Request`

```json
{ "message": "Only DRAFT production orders can be confirmed" }
```

### 6. Complete Production Order

```
POST /production-orders/:productionOrderId/complete
Permission: production-orders.update
```

Moves `IN_PROGRESS` → `COMPLETED`. The operator enters the actual output quantity; the backend finalizes
`totalCost` and computes `costPerUnit`.

#### Path Parameter

| Param | Type | Notes |
|---|---|---|
| `productionOrderId` | `uuid` | Must currently be `IN_PROGRESS` |

#### Request Body

```json
{
  "producedQuantity": 95
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `producedQuantity` | `number` | Yes | Must be ≥ 0. The actual quantity of finished product produced (may differ from `plannedQuantity`) |

#### Response `200 OK`

Full updated production order object — `status: "COMPLETED"`, `producedQuantity`, `completedAt`, `costPerUnit`
all set. `totalCost = rawMaterialCost + additionalCost + wasteInputCost` at this moment.

> If `producedQuantity` is `0`, `costPerUnit` is returned as `null` (avoids divide-by-zero).

#### Validation Error `400 Bad Request`

```json
{ "message": "Only IN_PROGRESS production orders can be completed" }
```

### 7. Cancel Production Order

```
POST /production-orders/:productionOrderId/cancel
Permission: production-orders.update
```

Moves `DRAFT` or `IN_PROGRESS` → `CANCELLED`. No request body.

- From `DRAFT`: releases all soft-reserved batch quantities back to available stock.
- From `IN_PROGRESS`: reverses all consumed batch quantities, restoring physical stock (`materials[].batchAllocations[].consumedAt` reset to `null`).

#### Path Parameter

| Param | Type | Notes |
|---|---|---|
| `productionOrderId` | `uuid` | Must be `DRAFT` or `IN_PROGRESS` |

#### Response `200 OK`

Full updated production order object — `status: "CANCELLED"`.

#### Validation Error `400 Bad Request`

```json
{ "message": "Cannot cancel a COMPLETED production order" }
{ "message": "Cannot cancel a CANCELLED production order" }
```

### 8. Add Cost Line

```
POST /production-orders/:productionOrderId/costs
Permission: production-orders.update
```

Adds a labour/overhead/utility/other cost line. Automatically recalculates `additionalCost` and `totalCost` (and
`costPerUnit` if the order is already `COMPLETED`).

Can be called **any number of times**, in any order relative to [Add Waste-as-Input Line](#9-add-waste-as-input-line),
as long as the order is not `CANCELLED` — including after completion.

#### Path Parameter

| Param | Type | Notes |
|---|---|---|
| `productionOrderId` | `uuid` | Must not be `CANCELLED` |

#### Request Body

```json
{
  "costType": "UTILITY",
  "description": "Electricity for production run",
  "amount": 200
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `costType` | `ProductionCostType` | Yes | `LABOUR`, `OVERHEAD`, `UTILITY`, `OTHER` |
| `description` | `string` | No | |
| `amount` | `number` | Yes | Must be > 0 |

#### Response `200 OK`

Full updated production order object — `costs[]` includes the new line, `additionalCost` and `totalCost`
recalculated (and `costPerUnit` if `COMPLETED`).

#### Validation Error `400 Bad Request`

```json
{ "message": "Cannot modify a CANCELLED production order" }
```

### 9. Add Waste-as-Input Line

```
POST /production-orders/:productionOrderId/wastes
Permission: production-orders.update
```

Reuses a `PENDING` raw-material waste record (from the Waste Management module — see
[waste-management-api.md](./waste-management-api.md)) as production input for this order. Marks that waste
record as `REUSED` and recalculates `wasteInputCost`/`totalCost` (and `costPerUnit` if `COMPLETED`).

#### Path Parameter

| Param | Type | Notes |
|---|---|---|
| `productionOrderId` | `uuid` | Must not be `CANCELLED` |

#### Request Body

```json
{
  "wasteManagementId": "waste-mgmt-uuid-1",
  "quantity": 10,
  "unitCost": 8,
  "totalCost": 80,
  "notes": "Recycled offcuts fed into this order"
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `wasteManagementId` | `uuid` | Yes | Must reference a `WasteManagement` record with `itemType: "RAW_MATERIAL"` and `status: "PENDING"` |
| `quantity` | `number` | Yes | Must be > 0 and ≤ the waste record's remaining `quantity` |
| `unitCost` | `number` | Yes | Must be ≥ 0 |
| `totalCost` | `number` | Yes | Must be ≥ 0. The frontend computes and sends this (typically `quantity × unitCost`) |
| `notes` | `string` | No | |

> `rawMaterialId` and `uomId` for the new `ProductionOrderWaste` row are derived server-side from the referenced
> waste record — do not send them.

#### Response `200 OK`

Full updated production order object — `wastes[]` includes the new line, `wasteInputCost` and `totalCost`
recalculated.

#### Validation Errors `400 Bad Request`

```json
{ "message": "Only raw material waste records can be reused as input" }
{ "message": "This waste record is not available for reuse" }
{ "message": "Quantity used (15) cannot exceed the available waste quantity (10)" }
{ "message": "Cannot modify a CANCELLED production order" }
```

#### Not Found `404`

```json
{
  "statusCode": 404,
  "message": "Waste management record not found",
  "error": "Not Found"
}
```

## Frontend Implementation Notes

### Decimal Fields

The following are Prisma `Decimal` fields and are returned as **strings** — always `parseFloat()` before display
or arithmetic:

`rawMaterialCost`, `additionalCost`, `wasteInputCost`, `totalCost`, `costPerUnit`,
`materials[].estimatedCost`, `materials[].actualCost`, `materials[].batchAllocations[].totalCost`,
`costs[].amount`, `wastes[].totalCost`.

`materials[].batchAllocations[].unitCost`, `wastes[].unitCost`, `wastes[].quantity` are plain numbers (`Float`).

### Status Badge Colors (suggested)

| `IN_PROGRESS` | Blue |

### Typical Screen Flows

**Production Orders List Screen**
- `GET /production-orders` with pagination, `status`, `productId`, `siteId` filters and search.
- Show `orderNumber`, `product.name`, `plannedQuantity`, `producedQuantity`, `status`, `totalCost`.

**Create Production Order Screen**
- User picks `productId` → load that product's **ACTIVE** BOMs (BOM dropdown filtered by product + `status: ACTIVE`).
- User picks `bomId`, `siteId` (optional), `plannedQuantity`, `notes`.
- On submit, call `POST /production-orders`. On `400` (insufficient stock), show the shortfall message returned
  and let the user reduce `plannedQuantity` or pick a different BOM/site.
- On success, navigate to the detail screen — order starts as `DRAFT`.

**Production Order Detail Screen**
- `GET /production-orders/:id` to load everything (header, materials, batch breakdown, costs, wastes).
- **Header card**: `orderNumber`, `status` badge, `product`, `bom`, `site`, `plannedQuantity` vs `producedQuantity`.
- **Cost summary card**: `rawMaterialCost`, `additionalCost`, `wasteInputCost`, `totalCost`, `costPerUnit`
  (show `—` if `null`).
- **Materials table**: one row per `materials[]` entry — `rawMaterial.name`, `requiredQuantity`,
  `consumedQuantity`, `uom.symbol`, `estimatedCost` / `actualCost`. Expandable sub-row for `batchAllocations[]`
  showing `rawMaterialBatch.batchNumber`, `allocatedQuantity`, `unitCost`, `totalCost`, and whether `consumedAt`
  is set (✅ consumed vs ⏳ reserved).
- **Costs table**: `costs[]` — `costType`, `description`, `amount`, `createdAt`.
- **Wastes table**: `wastes[]` — `rawMaterial.name`, `quantity`, `unitCost`, `totalCost`, `notes`.
- **Action buttons** (shown based on `status` and `production-orders.update` permission):
  - `DRAFT` → **Edit** (opens form for `siteId`/`notes` → `PATCH`), **Confirm** (→ `POST .../confirm`),
    **Cancel** (→ `POST .../cancel`, confirm dialog).
  - `IN_PROGRESS` → **Add Cost** (modal → `POST .../costs`), **Add Waste Input** (modal → `POST .../wastes`),
    **Complete** (modal asking for `producedQuantity` → `POST .../complete`), **Cancel** (confirm dialog,
    warn that it reverses stock consumption).
  - `COMPLETED` → **Add Cost** / **Add Waste Input** still available (late adjustments — recalculates
    `costPerUnit`). No Confirm/Complete/Cancel.
  - `CANCELLED` → read-only, no actions.
- **Audit history**: add a "View History" button calling
  `GET /audit-logs/entity/ProductionOrder/{productionOrderId}` — see
  [audit-logs-api.md](./audit-logs-api.md).

**Add Waste Input Modal**
- Let the user pick from `PENDING` `RAW_MATERIAL` waste records (from the Waste Management list, filtered to
  `itemType: RAW_MATERIAL`, `status: PENDING`).
- Pre-fill `unitCost` from the selected waste record if available; let the user enter `quantity` (capped at the
  waste record's remaining quantity) and compute `totalCost = quantity × unitCost` client-side before submitting.

**Complete Modal**
- Show `plannedQuantity` as a hint/default, but require the user to enter the actual `producedQuantity`.
- After completion, refresh the detail screen to show `costPerUnit`.
