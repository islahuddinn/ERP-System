## Overview

The Sales module covers the full customer sale lifecycle:

| Sub-module    | Base Path                       | Description                                              |
| ------------- | ------------------------------- | -------------------------------------------------------- |
| Sales         | `/sales`                        | Create, list, update, confirm, cancel sales              |
| Payments      | `/sales/:saleId/payments`       | Record and correct payments against a confirmed sale     |
| Returns       | `/sales/:saleId/returns`        | Return items from a completed sale (restores stock)      |
| Receipts      | `/receipts`                     | Generate PDF/thermal receipts; download; email           |

### Sale Lifecycle

```
DRAFT ──confirm──► COMPLETED
  │
  └──cancel────────► CANCELLED
```

- **DRAFT**: Initial state. Items are FIFO-reserved but stock is **not yet deducted**. Can be fully edited (items, customer, dates, discounts, tax) or cancelled.
- **COMPLETED**: Sale confirmed. Stock deducted, customer balance increased. Only `notes` can be changed. Use returns to reverse items.
- **CANCELLED**: Terminal. No stock impact. Cannot be modified.

### Payment Status

```
PENDING ──(first payment)──► PARTIAL ──(final payment)──► PAID
```

- `PENDING`: No payments recorded.
- `PARTIAL`: Payments recorded but `amountPaid < totalAmount`.
- `PAID`: `amountPaid >= totalAmount` (within 0.001 tolerance).

## Enums & Constants

### `SaleStatus`

```

COMPLETED  — Confirmed; stock deducted; customer balance debited
CANCELLED  — Terminal; reservations released
```

### `EPaymentStatus`

```
PENDING  — amountPaid = 0
PARTIAL  — 0 < amountPaid < totalAmount
PAID     — amountPaid >= totalAmount
```

### `PaymentMethod`

```

CARD
MOBILE_PAYMENT
BANK_TRANSFER

OTHER

```

### `SaleReturnStatus`

```

```

### `RefundStatus`

```

PROCESSED — Refund disbursed
FAILED    — Refund failed
```

### `ItemType`

```
PRODUCT   — Tracked inventory item (requires productId)
SERVICE   — Non-inventory line (no stock impact)
```

### Sale / Return Number Formats

Auto-generated by the backend:

- Sale: `SALE-YYYYMMDD-XXXX` (daily-sequential, zero-padded to 4)
- Return: `RET-YYYYMMDD-XXXX` (daily-sequential, zero-padded to 4)
- Examples: `SALE-20260618-0001`, `RET-20260618-0001`

### Decimal Fields

All monetary fields (`subtotal`, `itemsDiscountAmount`, `discountAmount`, `totalDiscountAmount`, `taxAmount`, `totalTaxAmount`, `totalAmount`, `amountPaid`, item `unitPrice`/`lineSubtotal`/`lineTotal`, payment `amount`, return `totalAmount`) are returned as **JS numbers** (serialized from Prisma `Decimal` by the response interceptor). No `parseFloat()` needed.

## Calculation Logic

Understanding how totals are computed is critical for building the create/edit sale form.

> **Rule**: The backend computes **all** totals — never send pre-calculated values. Send quantities, prices, and discount/tax inputs only; the backend computes everything else and returns it in the response.

---

### Calculation Flow (visual)

```
Per Item
─────────────────────────────────────────────────────────
  quantity × unitPrice  ──────────────────────►  lineSubtotal
                                                       │
  itemDiscountPercentage%  ──► itemDiscountFromPct     │
  itemDiscountAmount (flat) ──► itemDiscountFromAmt    │
  itemDiscountFromPct + itemDiscountFromAmt ──► itemTotalDiscountAmount
                                                       │
  lineSubtotal − itemTotalDiscountAmount  ─────────►  lineTotal ✓
  ⚠  lineTotal must be ≥ 0

Sale Aggregation
─────────────────────────────────────────────────────────
  SUM(lineSubtotal)            ──────────────►  subtotal
  SUM(itemTotalDiscountAmount) ──────────────►  itemsDiscountAmount
  subtotal − itemsDiscountAmount ─────────────►  netSubtotal

Sale-Level Discount  (applied to netSubtotal)
─────────────────────────────────────────────────────────
  netSubtotal × discountPercentage%  ──► saleDiscountFromPct
  discountAmount (flat)              ──► saleDiscountFromAmt
  saleDiscountFromPct + saleDiscountFromAmt ──► totalSaleDiscount
  itemsDiscountAmount + totalSaleDiscount   ──► totalDiscountAmount
  ⚠  totalSaleDiscount must be ≤ netSubtotal

Tax  (applied AFTER all discounts)
─────────────────────────────────────────────────────────
  netSubtotal − totalSaleDiscount  ──────────►  taxableAmount
  taxableAmount × taxPercentage%   ──► taxFromPct
  taxAmount (flat)                 ──► taxFromAmt
  taxFromPct + taxFromAmt          ──────────►  totalTaxAmount

Final
─────────────────────────────────────────────────────────
  taxableAmount + totalTaxAmount   ──────────►  totalAmount ✓
```

---

### Step-by-Step Formulas

#### Step 1 — Per Item (line level)

```
lineSubtotal            = quantity × unitPrice

itemDiscountFromPct     = lineSubtotal × (itemDiscountPercentage / 100)
itemDiscountFromAmt     = itemDiscountAmount          // flat Rs. discount
itemTotalDiscountAmount = itemDiscountFromPct + itemDiscountFromAmt

lineTotal               = lineSubtotal − itemTotalDiscountAmount

⚠  lineTotal must be ≥ 0  (item discounts cannot exceed the line subtotal)
```

**Both item discount types can be used together on the same line.**
Example: `itemDiscountPercentage=5` + `itemDiscountAmount=20` on a Rs. 1000 line → discount = 50 + 20 = 70 → lineTotal = 930.

#### Step 2 — Sale-level aggregation

```
subtotal             = SUM(lineSubtotal)             // all items
itemsDiscountAmount  = SUM(itemTotalDiscountAmount)  // all items
netSubtotal          = subtotal − itemsDiscountAmount
```

#### Step 3 — Sale-level discount (on top of item discounts)

```
saleDiscountFromPct  = netSubtotal × (discountPercentage / 100)
saleDiscountFromAmt  = discountAmount                // flat Rs. sale discount
totalSaleDiscount    = saleDiscountFromPct + saleDiscountFromAmt
totalDiscountAmount  = itemsDiscountAmount + totalSaleDiscount

⚠  totalSaleDiscount must be ≤ netSubtotal
```

**Both sale discount types can be used together.**

#### Step 4 — Tax (always after all discounts)

```
taxableAmount  = netSubtotal − totalSaleDiscount

taxFromPct     = taxableAmount × (taxPercentage / 100)
taxFromAmt     = taxAmount                           // flat Rs. tax amount
totalTaxAmount = taxFromPct + taxFromAmt
```

#### Step 5 — Final total

```
totalAmount = taxableAmount + totalTaxAmount
```

### Worked Example

```
Item A: qty=10, unitPrice=100, itemDiscountPercentage=0, itemDiscountAmount=0
  lineSubtotal = 1000
  itemTotalDiscountAmount = 0
  lineTotal = 1000

Item B: qty=5, unitPrice=200, itemDiscountPercentage=5, itemDiscountAmount=0
  lineSubtotal = 1000
  itemDiscountFromPct = 50
  itemTotalDiscountAmount = 50
  lineTotal = 950

── Aggregation ──────────────────────────────────
subtotal            = 2000
itemsDiscountAmount = 50
netSubtotal         = 1950

── Sale-level discount ──────────────────────────
discountPercentage  = 2%
saleDiscountFromPct = 1950 × 0.02 = 39
discountAmount      = 0  (no flat sale discount)
totalSaleDiscount   = 39
totalDiscountAmount = 50 + 39 = 89

── Tax ──────────────────────────────────────────
taxableAmount       = 1950 − 39 = 1911
taxPercentage       = 5%
taxFromPct          = 1911 × 0.05 = 95.55
taxAmount           = 0  (no flat tax)
totalTaxAmount      = 95.55

── Final ────────────────────────────────────────
totalAmount         = 1911 + 95.55 = 2006.55
```

### Live Preview (Frontend Pattern)

To show a running total as the user types — **before** they submit — implement the same formula client-side:

```ts
function computeSaleTotals(items, discountPercentage = 0, discountAmount = 0, taxPercentage = 0, taxAmount = 0) {
  const lines = items.map(item => {
    const lineSubtotal = item.quantity * item.unitPrice;
    const discFromPct  = lineSubtotal * ((item.itemDiscountPercentage ?? 0) / 100);
    const discFromAmt  = item.itemDiscountAmount ?? 0;
    const itemTotalDiscount = discFromPct + discFromAmt;
    return { lineSubtotal, itemTotalDiscount, lineTotal: lineSubtotal - itemTotalDiscount };
  });

  const subtotal            = lines.reduce((s, l) => s + l.lineSubtotal, 0);
  const itemsDiscountAmount = lines.reduce((s, l) => s + l.itemTotalDiscount, 0);
  const netSubtotal         = subtotal - itemsDiscountAmount;

  const saleDiscFromPct     = netSubtotal * (discountPercentage / 100);
  const saleDiscFromAmt     = discountAmount;
  const totalSaleDiscount   = saleDiscFromPct + saleDiscFromAmt;
  const totalDiscountAmount = itemsDiscountAmount + totalSaleDiscount;

  const taxableAmount       = netSubtotal - totalSaleDiscount;
  const taxFromPct          = taxableAmount * (taxPercentage / 100);
  const taxFromAmt          = taxAmount;
  const totalTaxAmount      = taxFromPct + taxFromAmt;

  return {
    subtotal,
    itemsDiscountAmount,
    netSubtotal,
    totalDiscountAmount,
    taxableAmount,
    totalTaxAmount,
    totalAmount: taxableAmount + totalTaxAmount,
  };
}
```

> The backend always recomputes these on submit — the client formula is only for live UI feedback. If the values differ by a rounding error (< 0.01), trust the backend value.

```
Permission: sales.create
```

### 4. Update Sale

```
PATCH /sales/:saleId
Permission: sales.update
```

Behavior depends on the current sale `status`:

| Status      | What can be updated                                                                |
| ----------- | ---------------------------------------------------------------------------------- |
| `DRAFT`     | `items` (full replacement), `customerId`, `saleDate`, `discountPercentage`, `discountAmount`, `taxPercentage`, `taxAmount`, `notes` |
| `COMPLETED` | `notes` only                                                                       |
| `CANCELLED` | Nothing — returns `400 Bad Request`                                               |

**Key rules for DRAFT updates:**

- If `items` is provided → all current items are deleted and replaced; FIFO reservations are released and re-reserved.
- If `discountPercentage`/`discountAmount`/`taxPercentage`/`taxAmount` are provided → `items` **must** also be provided in the same request (totals must be recalculated with new items).
- If only `customerId`/`saleDate`/`notes` change (no items), pricing fields are **not** allowed in that request.

#### Path Parameter

| Param    | Type   | Notes   |
| -------- | ------ | ------- |
| `saleId` | `uuid` | Sale ID |

#### Request Body

All fields optional. For a DRAFT full update (replace items + recalc totals):

```json
{
  "customerId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "saleDate": "2026-06-19",
  "items": [
    {
      "productId": "prod-uuid-1",
      "quantity": 12,
      "unitPrice": 95,
      "itemDiscountPercentage": 5
    }
  ],
  "discountPercentage": 0,
  "discountAmount": 0,
  "taxPercentage": 5,
  "taxAmount": 0,
  "notes": "Updated — added 2 units"
}
```

For a DRAFT metadata-only update (no items):

```json
{
  "customerId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "saleDate": "2026-06-20",
  "notes": "Changed delivery date"
}
```

For a COMPLETED update (notes only):

```json
{
  "notes": "Customer requested soft copy invoice"
}
```

#### Response `200 OK`

Full updated sale (same shape as [Create Sale response](#1-create-sale)).

#### Errors

```json
{ "statusCode": 400, "message": "Cancelled sales cannot be modified" }
{ "statusCode": 400, "message": "Cannot update pricing fields without providing updated items" }
{
  "statusCode": 400,
  "message": "Completed sales cannot have items, customer, date, or pricing fields changed"
}
```

### 5. Confirm Sale

```
POST /sales/:saleId/confirm
Permission: sales.update
```

Transitions a `DRAFT` sale to `COMPLETED`. This is the point of no return for stock deduction and customer balance.

**Side effects on confirm:**
1. FIFO batch reservations are converted to consumed stock (`reservedQuantity → consumedQuantity`).
2. `Product.currentStock` is decremented for each item.
3. A `CustomerTransaction` of type `SALE` is created (debit = `totalAmount`), increasing the customer's balance.
4. `Product.reservedStock` is decremented.

#### Path Parameter

| Param    | Type   | Notes   |
| -------- | ------ | ------- |
| `saleId` | `uuid` | Sale ID |

#### Request Body

No body required.

#### Response `200 OK`

Full sale with `status: "COMPLETED"`.

#### Errors

```json
{ "statusCode": 400, "message": "Sale cannot be confirmed because it has no items" }
{ "statusCode": 400, "message": "Only DRAFT sales can be confirmed" }
```

---

### 6. Cancel Sale

```
POST /sales/:saleId/cancel
Permission: sales.update
```

Transitions a `DRAFT` sale to `CANCELLED`. Releases all FIFO batch reservations (no stock deduction occurred so nothing to reverse).

**Cannot cancel a `COMPLETED` sale** — use a [Sale Return](#1-create-return) instead.

#### Path Parameter

| Param    | Type   | Notes   |
| -------- | ------ | ------- |
| `saleId` | `uuid` | Sale ID |

#### Request Body

No body required.

#### Response `200 OK`

Full sale with `status: "CANCELLED"`.

#### Errors

```json
{ "statusCode": 400, "message": "Only DRAFT sales can be cancelled" }
{ "statusCode": 400, "message": "Completed sales cannot be cancelled — create a return instead" }
```

## Payments API

All payment endpoints are nested under a sale.

### 1. Record Payment

```
POST /sales/:saleId/payments
Permission: sales.update
```

Records a new payment against a `COMPLETED` sale. Recalculates `amountPaid` and `paymentStatus` atomically. Also creates a `CustomerTransaction` of type `PAYMENT` (credit), decreasing the customer's balance.

**Business Rules:**
- Sale must be `COMPLETED`.
- `amount` cannot exceed remaining balance (`totalAmount − amountPaid`).
- `paymentStatus` becomes `PAID` when `Math.abs(newAmountPaid − totalAmount) < 0.001`.

#### Path Parameter

| Param    | Type   | Notes   |
| -------- | ------ | ------- |
| `saleId` | `uuid` | Sale ID |

#### Request Body

```json
{
  "amount": 1000,
  "paymentMethod": "CASH",
  "referenceNumber": "TXN-001",
  "paymentDate": "2026-06-18",
  "notes": "Partial cash payment"
}
```

| Field             | Type            | Required | Notes                                                   |
| ----------------- | --------------- | -------- | ------------------------------------------------------- |
| `amount`          | `number`        | Yes      | Min 0.01; must not exceed remaining balance             |
| `paymentMethod`   | `PaymentMethod` | Yes      | `CASH`, `CARD`, `MOBILE_PAYMENT`, `BANK_TRANSFER`, etc. |
| `referenceNumber` | `string`        | No       | TXN ID, cheque number, etc.                             |
| `paymentDate`     | `ISO date string`| No      | Defaults to current datetime                            |
| `notes`           | `string`        | No       |                                                         |

#### Response `200 OK`

Full updated sale (same shape as [Create Sale response](#1-create-sale)), with `amountPaid`, `paymentStatus`, and `payments[]` updated.

#### Errors


## Sale Returns API

### 1. Create Return

## Stock Reservation System (FIFO)

Understanding the reservation flow helps explain why stock appears "held" during a draft sale.

### Phase 1 — DRAFT Creation (Reserve)

1. Fetch all `ACTIVE` batches for the product ordered by `createdAt ASC` (oldest first — FIFO).
2. Check `SUM(availableQuantity)` ≥ requested quantity.
3. For each batch: decrement `availableQuantity`, increment `reservedQuantity`.
4. Increment `Product.reservedStock`.
5. `Product.currentStock` is **not changed** yet.

### Phase 2 — DRAFT Update (Release & Re-reserve)

Whenever items are replaced:
1. Release previous reservations (reverse Phase 1).
2. Re-reserve with the new quantities and items (re-run Phase 1).

### Phase 3 — Confirm (Reserve → Consume)

1. Convert reserved batches: decrement `reservedQuantity`, increment `consumedQuantity`.
2. Decrement `Product.currentStock` (actual stock deduction happens here).
3. Decrement `Product.reservedStock`.

### Phase 4 — Cancel (Release)

1. Release all reservations (same as release step in Phase 2).
2. No stock is deducted.

### Phase 5 — Return (LIFO Restore)

1. Find the most recently created `ACTIVE` batch (LIFO for restoring returned goods).
2. Increment `availableQuantity`, decrement `consumedQuantity`, increment `returnedQuantity`.
3. Increment `Product.currentStock`.

## Customer Ledger Integration

| Action                     | `CustomerTransaction` type | Debit          | Credit         | Balance Impact         |
| -------------------------- | -------------------------- | -------------- | -------------- | ---------------------- |
| Confirm sale               | `SALE`                     | `totalAmount`  | 0              | Balance increases      |
| Record payment             | `PAYMENT`                  | 0              | `amount`       | Balance decreases      |
| Update payment (amount up) | `ADJUSTMENT`               | 0              | delta amount   | Balance decreases      |
| Update payment (amount down)| `ADJUSTMENT`              | delta amount   | 0              | Balance increases      |
| Create return              | `RETURN`                   | 0              | `returnTotal`  | Balance decreases      |
